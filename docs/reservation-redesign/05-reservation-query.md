# 예약·좌석 조회

> 구현 예정 설계다. 조회 결과는 표시용 스냅샷이며 실제 예약 가능 여부는 생성 Lua에서 확정한다.

[문서 목록](./README.md) · [이전: 예약 생성](./04-reservation-create.md) · [다음: 취소·만료](./06-reservation-cancel-expire.md)

## 목적

사용자에게 예약 상태·남은 시간·운임을 제공하고 좌석 선택 화면에 해당 구간의 가용성을 표시한다. 예약 상세의 원본은 Redis `reservations`, 확정된 예매·승차권의 원본은 DB다.

별도 Reservation DB 테이블은 만들지 않는다. 결제 준비 이후에는 DB 주문 상세에 예약 스냅샷이 남지만, 이것을 현재 예약의 유효성을 판단하는 원본으로 사용하지 않는다.

## 상세 조회의 선행 조건과 계약

```text
조회 식별자: trainScheduleId + reservationId
조회 권한: 인증된 memberNo == Reservation.memberNo
응답: 예약·좌석·운임, effectiveStatus, expiresAt, serverTime
```

예약 ID만으로 운행 일정의 hash slot을 역으로 찾는 기능은 핵심 키에 없다. 생성 응답에 두 식별자를 포함한다. ID에 운행 일정을 인코딩할지는 별도 결정 사항이며, 클라이언트 값은 반드시 예약 본문과 대조한다.

다른 회원의 예약과 없는 예약의 응답 구분은 정보 노출을 고려해 API 정책으로 정한다. 로그에는 필요한 식별자만 남기고 결제 키·개인정보를 그대로 출력하지 않는다.

## 상세 조회의 읽기·쓰기

| 대상 | 처리 |
|---|---|
| `meta` | 현재 판매·복구 상태와 세대 확인 |
| `reservations` | 지정한 예약의 본문과 저장 상태 조회 |
| Redis 현재 시각 | 논리 만료와 남은 시간 계산 |
| `occupancy` | 상세 화면에서는 선택적 진단; 결제 등 상태 변경 시 전체 검증 필수 |
| DB | 일반 예약 상세 조회에 사용하지 않음 |

기본 조회는 쓰기를 하지 않는다. Worker가 아직 실행되지 않은 만료 예약도 정상적으로 표현할 수 있어야 한다.

## 저장 상태와 논리 상태

```text
storedStatus = HELD
expiresAt    = 10:10
Redis now    = 10:11

effectiveStatus = EXPIRED
remainingTime   = 0
```

저장 상태가 `HELD`여도 이미 만료되었다면 응답은 사용 가능한 예약처럼 표시하지 않는다. Worker는 이후 저장 상태를 `EXPIRED`로 변경한다. 조회 응답의 필드명은 결정 사항이며, 내부 저장 상태와 화면의 유효 상태를 혼동하지 않는 것이 핵심이다.

| 저장 상태 | 시각 조건 | 조회 해석 |
|---|---|---|
| `HELD` | `now < expiresAt` | 유효한 예약 |
| `HELD` | `now >= expiresAt` | 논리 만료 |
| `CONFIRMING` | 원래 `expiresAt`과 무관 | 결제 확인 중, 좌석 점유 유지 |
| `CONFIRMED` | 임시 예약 시각과 무관 | 예매 확정, DB 예매·승차권으로 안내 |
| `CANCELLED/EXPIRED` | 무관 | 종료된 예약 |

시각과 본문을 함께 읽어야 한다면 짧은 조회용 Lua를 사용한다. 앱 시계만으로 권위 있는 만료 결정을 하지 않는다. 조회 후 상태가 바뀔 수 있으므로 후속 변경은 항상 Lua에서 다시 검증한다.

## 회원별 예약 목록

회원별 목록은 운행 일정별 `reservations` HASH만으로 효율적으로 찾기 어렵다. 별도 회원 인덱스가 필요하며 **핵심 5개 키 계산에는 포함하지 않는다**.

가능한 계약은 회원 인덱스가 `scheduleId + reservationId` 참조만 보유하고, 목록 조회 시 원본 예약을 읽어 권한·논리 만료를 재확인하는 것이다.

- 종료·삭제된 예약을 가리키는 항목은 조회에서 제외하고 보정한다.
- 목록에서 빠졌다고 예약 자체가 없다고 판단하지 않는다.
- 생성 직후 상세 조회는 생성 응답의 두 식별자로 바로 가능해야 한다.
- 회원 인덱스는 운행 일정과 다른 slot일 수 있어 생성 Lua와 한 번에 원자적으로 갱신할 수 있다고 가정하지 않는다.
- Stream을 사용하지 않으므로 인덱스 갱신 실패를 보정하는 스캔·대조 방식과 일관성 SLA를 구현 전에 결정한다.

첫 구현에서 목록을 제공하지 않고 상세만 지원할지, 보정 가능한 인덱스를 함께 구현할지는 [로드맵](./roadmap.md)에서 확정한다. 이 문서는 회원 인덱스의 정확한 키 이름·보존 정책을 확정하지 않는다.

## 좌석 가용성 조회

요청한 운행 일정·구간·객차 또는 등급에 속한 좌석을 기준정보에서 가져오고, 해당 좌석들의 구간별 `occupancy`를 조회한다. 점유 소유자의 Reservation 상태에 따라 사용 가능 여부를 결정한다.

```text
조회 구간: 서울(0) → 동대구(2)
좌석 12:
  12:0 → res_A
  12:1 → res_A
res_A = HELD, 만료 전

결과: 12번 사용 불가, 점유 좌석 수 +1
```

한 좌석이 여러 구간에서 점유되어도 좌석 수는 한 번만 센다. 요청 구간 중 하나라도 유효한 점유가 있으면 해당 좌석은 예약할 수 없다.

**Redis가 확정 점유까지 포함하므로 `전체 - DB 예매 - Redis 점유`로 계산하지 않는다.** 해당 구간의 Redis 유효 점유 좌석을 중복 제거해서 차감한다. DB는 장애 대조·복구에 사용한다.

많은 좌석을 읽는 Lua는 실행 시간을 제한해야 한다. 객차별 페이지·배치, 요청 최대 좌석 수, 캐시 가능한 표시 결과 등을 부하 측정에 따라 결정한다. 순차 읽기의 순간적 불일치를 허용한다면 표시 스냅샷임을 전제로 하고 실제 선점은 생성 Lua에 맡긴다.

## 실패·동시성 처리

- 조회 후 다른 요청이 좌석을 선점할 수 있다. 사용 가능 화면은 예약 성공을 보장하지 않는다.
- 점유 소유자는 있는데 예약 본문이 없으면 해당 재고를 사용 가능으로 표시하지 않는다. 데이터 오류·복구 대상으로 분류한다.
- `meta`가 준비되지 않았거나 복구 중이면 정상적인 빈 좌석 결과를 반환하지 않는다.
- Redis 장애 시 DB의 주문 스냅샷으로 현재 예약이 유효하다고 추정하지 않는다.
- TTL로 본문이 사라지는 것을 만료 판정 규칙으로 사용하지 않는다.
- 종료 데이터 보존 기간 이후 상세를 더 이상 제공하지 않는 정책은 명시적인 API 계약으로 정한다.

## 수용 기준

- [ ] 타인의 예약 정보는 조회할 수 없다.
- [ ] Worker 지연 중에도 `HELD + expiresAt 경과`를 만료로 표시한다.
- [ ] `CONFIRMING`을 원래 예약 시각 경과만으로 만료 표시하지 않는다.
- [ ] 구간별 점유를 좌석별로 중복 제거하고 DB 확정 예매를 다시 차감하지 않는다.
- [ ] 조회·생성 경합에서 최종 판단을 생성 Lua가 수행한다.
- [ ] 회원 목록 인덱스가 오래되거나 누락된 경우의 복구·표시 계약이 정해져 있다.
- [ ] 복구 중·기준정보 누락·점유 소유자 누락을 빈 재고와 구분한다.
