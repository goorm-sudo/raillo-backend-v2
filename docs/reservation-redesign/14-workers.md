# Worker와 정리 작업

> 구현 예정 설계다. Worker는 애플리케이션 내부 스케줄러로 시작할 수 있다. 여러 인스턴스의 중복 실행과 프로세스 종료를 전제로 설계한다.

관련: [Redis 키](12-redis-keys.md), [Lua](13-lua-scripts.md), [결제 실패·복구](10-payment-failure-recovery.md)

## 1. 필요한 Worker

| Worker | 후보의 기준 | 주된 책임 |
|---|---|---|
| `ReservationExpiryWorker` | Redis `deadlines` | 만료된 `HELD` 예약의 점유·상태 정리 |
| `PaymentRecoveryWorker` | DB 미완료 승인 시도, Redis `confirmation-deadlines` | 결제 결과 확인·확정 재시도·실패 또는 취소 보상 |
| `OutboxWorker` | DB 미처리 Outbox | 커밋된 결제·예매 결과를 Redis에 반영 |
| `ReservationCleanupWorker` | 종료 시각·보존 기한 | 안전하게 종료된 예약·멱등성·조회 인덱스 정리 |

Worker는 실행 시점·배치·재시도를 담당한다. 업무 규칙과 상태 변경은 유스케이스·Service·Lua에 둔다. Service가 다른 Service를 직접 호출하는 구조는 만들지 않는다.

## 2. 예약 만료 Worker

`deadlines`의 score는 예약 `expiresAt`이다. **이 시각에 예약이 무효가 되며, Worker는 남은 데이터를 정리한다.**

```text
deadlines
  res_A → 10:10
  res_B → 10:15

현재 시각 10:11
  → 만료 후보 res_A 조회
  → expire_reservation.lua(res_A)
```

권장 실행 절차는 다음과 같다.

1. 처리 대상 운행 일정 목록에서 이번 배치를 선택한다.
2. Redis 시각을 기준으로 현재 시각 이하의 ZSET 멤버를 제한된 수만 조회한다.
3. 항목을 먼저 제거하지 않고 예약별 만료 Lua를 호출한다.
4. Lua에서 `HELD`, 실제 `expiresAt`, 세대, 현재 점유 소유자를 다시 검사한다.
5. 유효한 만료이면 소유 점유를 해제하고 `EXPIRED`로 변경한 뒤 ZSET에서 제거한다.
6. 일시 실패 항목은 다음 실행에서 다시 처리한다.

ZSET은 score 범위로 조회할 수 있다. 쿼리 형태는 `ZRANGE key -inf now BYSCORE LIMIT 0 batchSize`이며 숫자 시각과 배치 크기는 런타임 인자로 전달한다. [Redis ZRANGE](https://redis.io/docs/latest/commands/zrange/)

`ZPOPMIN`처럼 조회와 함께 후보를 제거한 뒤 외부 처리를 시작하지 않는다. 제거 직후 프로세스가 종료되면 미처리 대상을 잃을 수 있다.

### 경합 처리

| 경합 | 처리 |
|---|---|
| 두 Worker가 같은 예약 조회 | 첫 Lua가 만료 처리, 다음 Lua는 종료 상태를 확인 |
| 승인 진입이 먼저 성공 | `CONFIRMING`을 확인하고 만료 처리하지 않음 |
| 만료 처리가 먼저 성공 | 뒤늦은 승인 진입 거부 |
| 새 예약이 만료 점유를 재사용 | 소유자가 달라진 점유는 삭제하지 않음 |
| 후보는 있지만 본문이 없음 | 정상 만료로 처리하지 않고 불일치 복구 대상으로 기록 |

Lua는 다른 요청이 끼어들지 않는 범위에서 상태를 검사·변경한다. 입력·타입·직렬화 검증을 쓰기 전에 끝내고, 실행 오류가 앞선 쓰기를 자동 롤백한다고 가정하지 않는다. [Redis Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)

## 3. 결제 복구 Worker

**DB 미완료 승인 시도가 복구 대상의 기준이다.** Redis 인덱스는 빠른 후보 탐색을 돕는다. DB 기록 직후 Redis 변경 전에 프로세스가 종료될 수 있으므로 Redis만 조회해서는 안 된다.

```text
DB 미완료 승인 시도 ─────┐
                         ├─ attemptId로 중복 제거 → 처리 권한 확보 → 결과 확인
Redis 확인 기한 도래 ────┘
```

1. DB의 `nextRetryAt`이 지난 미완료 시도를 제한된 수만 확보한다.
2. Redis 인덱스로 발견한 시도도 DB 상태와 대조한다.
3. DB 조건부 갱신으로 처리 권한을 확보하고 이미 완료되었는지 재확인한다.
4. 결제 결과 조회·DB 예매 확정·취소 보상 중 필요한 유스케이스를 실행한다.
5. Redis 결과 반영은 커밋된 Outbox로 연결한다.
6. 결과가 불명확하면 `CONFIRMING` 점유를 유지하고 다음 확인 시각을 등록한다.

`confirmation-deadlines`는 자동 해제 시각이 아니다. 그 시각이 지났다는 이유로 `fail_confirmation.lua`를 호출하지 않는다.

외부 요청은 DB 트랜잭션 밖에서 호출한다. 처리 lease·fencing token은 DB 경합을 통제하지만 외부 승인 dispatch 경계를 완전히 해결하지 않는다. 오래된 호출자가 다시 승인할 가능성이 남았다면 조회 not-found만으로 점유를 해제하지 않는다. 자세한 계약은 [결제 실패·복구](10-payment-failure-recovery.md)를 따른다.

결제 준비 중 주문 연결만 완료된 채 중단되는 경우도 복구해야 한다. 결제 준비 intent를 DB에 먼저 기록하고, 미완료 준비 기록을 이 Worker의 별도 배치에서 대조한다. 정확한 테이블·상태 저장 위치는 [결제 준비](07-payment-prepare.md)의 구현 전 결정 사항이다.

## 4. Outbox Worker

1. DB에서 실행 가능한 미처리 작업을 배치로 확보한다.
2. 예약별 선행 작업·DB 상태·sequence를 확인한다.
3. 해당 운행 일정의 Lua에 작업 식별자와 기대 상태를 전달한다.
4. 적용 완료 또는 같은 작업의 완료를 확인한 경우에만 DB 결과를 기록한다.
5. 일부 예약만 성공했으면 대상별 진행 상황을 남기고 나머지를 재시도한다.

Redis 호출이 성공한 직후 DB 완료 기록 전에 종료될 수 있으므로 같은 작업은 다시 전달된다. Lua의 멱등성과 순서 검증이 필수다. Worker의 상세 계약은 [Outbox](15-outbox.md)에 둔다.

## 5. 종료 데이터 정리 Worker

예약 유효기간과 데이터 보존 기한은 구분한다. `EXPIRED`·`CANCELLED` 예약도 API 재시도, 늦은 작업 식별, 운영 확인을 위해 일정 기간 보존한다.

삭제 전 다음을 확인한다.

- 종료 상태이며 보존 기한을 지났는가?
- 해당 예약이 소유한 활성 점유가 없는가?
- 결제·Outbox·복구 진행 중인 참조가 없는가?
- 멱등성 재시도 보장 기간이 끝났는가?

`CONFIRMING`은 정리하지 않는다. 판매 기간 중 좌석 점유를 판단하는 `CONFIRMED` 본문도 삭제하지 않는다. 운행 종료 후 확정 데이터 정리는 판매 종료·결제 복구·예매 취소 처리 정책을 확인한 뒤 수행한다.

`reservations` HASH는 필드별 종료 시각을 읽을 수 있도록 `HSCAN` 배치 순회로 시작할 수 있다. 필요 시 별도 보존 기한 ZSET을 도입하되, 이는 핵심 Redis 키 5개에 포함되지 않는 추가 인덱스다.

멱등성 기록이 삭제된 예약을 가리키지 않도록 보존 기간을 맞춘다. 예약 본문보다 기록을 오래 보존해야 한다면 종료 결과 스냅샷 또는 tombstone을 남기고, 그 결과가 언제까지 조회 가능한지 API 계약에 명시한다. 삭제 뒤 동일 요청을 신규 요청으로 취급할 수 있는 시점도 고정한다.

## 6. 스케줄·처리 대상 탐색

예약·확인 기한 ZSET은 운행 일정별로 나뉜다. Worker는 DB의 판매 대상 운행 목록 또는 별도 운영 인덱스로 처리할 운행을 찾아야 한다. 매 실행마다 전체 Redis 키를 조회하지 않는다.

운영 인덱스를 사용한다면 생성 API의 교차 slot 갱신을 유일한 등록 경로로 삼지 않는다. 적재·판매 준비 단계에서 먼저 등록하고 DB 목록과 주기적으로 대조하여 누락을 복구한다.

| 설정 | 예시 | 구현 시 검증 |
|---|---|---|
| 예약 만료 조회 주기 | 1초 | Redis 부하와 물리 정리 지연 |
| 만료 후보 배치 | 운행별 100건 | 한 운행이 다른 운행 처리를 독점하지 않는지 |
| 복구·Outbox 재시도 | 지수 backoff + jitter | 최대 지연·결제사 한도·멱등성 보장 기간 |
| 정리 작업 주기 | 낮은 빈도의 배치 | 보존 기간·운영량 |

숫자는 설계 예시이며 확정 운영값이 아니다. 긴 Lua·무제한 재조회 루프를 피하고, 대상별 동시 실행 수·한 회차 처리량을 제한한다.

## 7. 별도로 필요한 작업

| 작업 | 실행 계기 | 책임 |
|---|---|---|
| 기준정보 적재·갱신 | 판매 준비, 운행·운임 변경 | `meta/stops/seats/fares` 버전과 판매 가능 상태 관리 |
| 재고 복구 | Redis 유실·세대 변경·점유 불일치 | 판매 차단, DB 확정 예매·미완료 결제 대조, 점유 복구 |
| 운영 수동 복구 | 자동 처리 한도 초과 | 실제 결제 결과 대조 후 같은 유스케이스로 재처리 |

일반 만료 Worker가 재고 복구까지 수행하지 않는다. Redis 장애 후 예약이 없다는 사실만으로 판매를 재개하지 않는다.

## 8. 관측과 검증

- 가장 오래된 만료 후보·미완료 승인·Outbox의 경과 시간과 처리량을 기록한다.
- 상태 불일치, 세대 불일치, 소유자 불일치, 외부 결과 미확인 건수를 구분한다.
- 일시 실패와 운영 복구 대상은 별도로 관리하고 재시도 횟수 초과를 완료로 표시하지 않는다.
- 중복 실행, 후보 조회 직후 종료, Redis 성공 직후 DB 기록 실패를 검증한다.
