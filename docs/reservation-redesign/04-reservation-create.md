# 예약 생성

> 구현 예정 설계다. 이벤트·Redis Stream 발행과 Reservation DB 저장은 포함하지 않는다.

[문서 목록](./README.md) · [로드맵](./roadmap.md) · [다음: 예약 조회](./05-reservation-query.md)

## 목적과 처리 단위

하나의 운행 일정에서 여러 좌석을 같은 구간으로 예약한다. 요청한 모든 좌석을 먼저 검증한 뒤 `HELD` 예약과 점유를 저장한다. 예약 생성 과정의 운행·좌석·운임 조회는 Redis 기준정보를 사용한다.

서로 다른 운행 일정의 예약은 각각 생성한다. 여러 예약을 함께 결제하는 것은 Order의 책임이며, 서로 다른 Redis slot의 예약을 단일 Lua로 처리하지 않는다.

## 선행 조건

- `meta.status == READY`이고 기준정보가 완전해야 한다.
- DB의 확정 예매와 결제 진행 중 점유가 Redis에 반영되어 있어야 한다.
- 요청한 역이 해당 운행 일정의 정차역이며 출발 순서가 도착 순서보다 작아야 한다.
- 좌석은 해당 열차의 유효한 좌석이어야 한다. 좌석 중복·최대 개수·승객 유형을 검증한다.
- 서버가 인증 정보에서 회원 식별자를 결정한다. 클라이언트의 회원 번호나 계산 금액을 신뢰하지 않는다.
- 정차 순서는 인접 구간을 만들 수 있는 연속 ordinal로 정의한다. DB 순번이 불연속이라면 적재 시 정규화한다.

## 요청과 응답

```text
요청: trainScheduleId, departureStationId, arrivalStationId,
      seats[{seatId, passengerType}]
헤더: Idempotency-Key
인증: memberNo

응답: trainScheduleId, reservationId, status,
      seats, totalFare, createdAt, expiresAt
```

API 경로·성공 코드·오류 코드는 구현 단계에서 프로젝트 규칙에 맞춰 정한다. 기준정보 버전이나 복구 세대는 서버 내부 계약이며 사용자 입력으로 결정하지 않는다.

## 읽기·쓰기 대상

| 구분 | 대상 | 용도 |
|---|---|---|
| Redis 읽기 | `meta`, `stops`, `seats`, `fares` | 판매 상태·역·좌석·운임·버전 확인 |
| Redis 읽기/쓰기 | `reservations`, `occupancy` | 예약 상태·좌석 구간 소유자 |
| Redis 쓰기 | `deadlines`, `idempotency` | 만료 후보와 재시도 결과 |
| DB | 없음 | Reservation INSERT나 실시간 좌석 충돌 SELECT 없음 |

예약 생성 성공 시 변경하는 핵심 키는 **4개**다. `confirmation-deadlines`는 승인 진입에서 사용한다. 키의 전체 이름은 [Redis 키](./12-redis-keys.md)를 따른다.

## 서버 처리

1. 요청과 인증 정보를 검증하고 멱등성 키를 확보한다.
2. Redis에서 일관된 기준정보 버전의 스냅샷을 조회한다.
3. Java `BigDecimal`로 좌석별 운임과 총액을 계산한다.
4. 기준정보 버전·복구 세대·예약 ID·운임 스냅샷·정규화된 요청 해시를 Lua에 전달한다.
5. Lua 결과를 성공, 충돌, 재시도 가능한 버전 변경, 데이터 오류 등으로 변환한다.

여러 키로 기준정보를 읽는 동안 갱신이 일어날 수 있다. 버전 전후 확인 또는 같은 버전의 원자적 게시 규약으로 일관된 읽기를 보장해야 한다. Lua는 계산에 사용한 버전이 여전히 현재 버전인지 최종 확인한다.

## `create_reservation.lua`

검증 단계에서는 예약 관련 쓰기를 하지 않는다.

1. 입력 개수·형식·키 타입·직렬화 가능 여부를 확인한다.
2. 동일 회원의 멱등성 기록을 조회한다. 같은 내용이면 기존 예약을 반환하고, 다른 내용이면 거부한다. 신규 요청일 때만 생성할 예약 ID의 충돌 여부를 확인한다.
3. `meta`의 판매 상태·버전·복구 세대와 유효한 좌석·구간을 확인한다.
4. Redis `TIME`을 기준으로 출발 제한을 확인하고 만료 시각을 결정한다.
5. 모든 요청 좌석의 `[departureOrder, arrivalOrder)` 구간을 조회한다.
6. 소유 예약이 `HELD`이면 `expiresAt`, `CONFIRMING/CONFIRMED`이면 상태로 충돌을 판단한다.
7. 점유 소유자의 예약 본문이 없거나 파싱 불가능하면 예약을 차단하고 복구 대상으로 처리한다.

전체 검증을 통과한 뒤 예약 본문, 모든 점유 필드, 만료 인덱스, 멱등성 기록을 저장한다. Redis 기준 시각으로 `createdAt`을 정하고 아래 식으로 `expiresAt`을 정한다.

```text
expiresAt = min(now + holdDuration, boardingDepartureAt - salesCutoff)
```

`holdDuration`, `salesCutoff`는 정책 확정이 필요하다. 시간은 UTC Unix timestamp(ms)로 저장하며 예시의 10분은 확정 설정값이 아니다.

## 좌석·구간 예시

```text
서울(0) → 대전(1) → 동대구(2) → 부산(3)
A: 좌석 [12, 13], 서울 → 동대구

occupancy
  12:0 → res_A
  12:1 → res_A
  13:0 → res_A
  13:1 → res_A
```

B가 12번 대전→부산을 요청하면 `12:1`에서 충돌하므로 **요청 전체를 거부**한다. 비어 있는 `12:2`도 선점하지 않는다. B가 동대구→부산만 요청하면 `12:2`가 비어 있으므로 예약할 수 있다.

## 동시성·멱등성·실패

- 같은 구간의 동시 요청은 Lua 실행 순서대로 확인하며 첫 유효 점유 이후 요청은 충돌한다.
- 만료된 `HELD` 점유는 재사용할 수 있다. 기존 예약의 다른 구간을 무조건 지우지는 않는다.
- 멱등성 키는 `memberNo + requestKey`이며 요청 해시는 운행·구간·좌석·승객 유형을 정규화해서 계산한다. 서버 계산 결과나 현재 시각 때문에 같은 요청의 해시가 바뀌지 않도록 한다.
- 응답 유실 후 같은 요청은 기존 예약을 반환한다. 만료·취소된 예약은 종료 상태를 반환하며 유효기간을 연장하지 않는다.
- 기준정보 버전 변경은 새 스냅샷으로 계산해 제한적으로 재시도한다. 충돌은 자동으로 다른 좌석을 예약하지 않는다.
- 검증 단계의 비즈니스 거부는 쓰기 없이 끝낸다. **Lua 런타임 오류는 이전 쓰기를 자동 롤백하지 않는다.** 작업 식별자와 불변식 대조로 부분 쓰기를 감지하고 판매 차단·복구 경로를 마련한다.
- 멱등성 기록만으로 전체 저장 성공을 단정하지 않는다. 기록과 예약·점유가 불일치하면 성공을 재생하지 않고 복구한다.

## 수용 기준

- [ ] DB 조회·쓰기 없이 예약 생성이 완료된다.
- [ ] 여러 좌석 중 하나가 충돌하면 나머지 좌석도 선점하지 않는다.
- [ ] 같은 좌석의 비중첩 구간은 허용하고 중첩 구간은 거부한다.
- [ ] 동시 요청과 동일 요청 재시도에서 중복 예약·만료 연장이 없다.
- [ ] 기준정보 누락·갱신 경합·복구 세대 불일치 시 잘못된 예약을 만들지 않는다.
- [ ] Worker 지연과 무관하게 만료된 점유를 재사용할 수 있다.
- [ ] `CONFIRMING/CONFIRMED` 점유를 만료된 `HELD`처럼 재사용하지 않는다.
- [ ] Lua 부분 실패·응답 유실 후 불완전한 상태를 정상 성공으로 반환하지 않는다.
