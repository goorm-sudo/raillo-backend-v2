# 결제 승인

[목록](README.md) · [이전: 결제 준비](07-payment-prepare.md) · [다음: 예매 확정](09-booking-finalize.md)

> 구현 예정 설계. 사용자의 결제창 인증과 서버의 외부 승인 호출을 구분한다. 이 문서는 즉시 승인 결제수단을 대상으로 한다.

## 1. 결제창에서 서버로 넘어오는 값

결제 준비 응답의 orderId·amount로 결제창을 열고 인증이 완료되면 paymentKey·orderId·amount를 서버 승인 API에 전달한다. 성공 URL 도착만으로 Booking을 만들지 않는다. [토스 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)

서버는 클라이언트 금액을 신뢰하지 않고 주문·Payment·요청을 대조한다. 준비가 완료된 본인 주문인지, 이미 승인 완료/실패/복구 중인지 확인한다.

## 2. 승인 시도 기록

외부 호출 전 짧은 DB 트랜잭션으로 다음을 영속화한다.

- 안정적인 attemptId, Payment·주문 식별자, paymentKey.
- 원본 예약 참조·세대와 대상별 승인 진입 진행 상태.
- 처리 단계, 처리 권한·조건부 갱신 버전, 재확인 기한.
- 동일 승인 요청의 멱등성 결과 또는 진행 중 결과.

같은 주문에 대한 두 요청이 조회를 동시에 통과할 수 있으므로 DB 고유 제약·조건부 상태 전이를 사용한다. 이미 진행 중인 시도를 다른 결제로 덮어쓰지 않는다. 구체적인 enum은 미결정이며 업무 결제 상태와 처리 진척을 구분해 정의한다.

## 3. Redis 승인 진입

`begin_confirmation.lua`는 다음을 확인한다.

1. Reservation이 본인 주문에 연결되어 있는가?
2. 현재 상태가 HELD이고 Redis now가 expiresAt보다 작은가?
3. 모든 좌석·구간의 occupancy 소유자가 해당 예약인가?
4. 기준정보 판매/승인 조건·generation이 유효한가?
5. 동일 attemptId의 재시도인지, 다른 시도가 이미 진입했는가?

검증 후 함께 변경한다.

```text
reservations: HELD → CONFIRMING, attemptId·version 기록
deadlines: 예약 ID 제거
confirmation-deadlines: 결과 확인 기한 등록
occupancy: 유지
```

CONFIRMING으로 바뀐 뒤에는 원래 expiresAt으로 만료시키지 않는다. 조회 화면도 만료 대신 결제 확인 중을 표시한다.

## 4. 외부 호출 경계

```text
DB 승인 시도 커밋
  → 예약별 CONFIRMING 진입
  → DB에 전체 진입 성공·승인 전송 단계 기록
  → 결제사 승인 호출 (DB 트랜잭션 밖)
  → 결과 분류
```

전송 단계가 기록된 뒤 실제 HTTP 호출 전에 서버가 멈출 수 있다. 반대로 승인 성공 후 결과 기록 전에 멈출 수도 있다. 어느 경우든 외부 호출이 있었는지 확실하지 않은 상태를 표현해야 한다.

DB lease 만료만으로 이전 실행자의 네트워크 호출이 취소되는 것은 아니다. 오래된 실행자가 뒤늦게 승인하지 못하도록 제어하는 방법과 provider 멱등성 키의 scope·보존 시간·동일 payload 규칙을 구현 전 확정한다. 해당 계약을 검증하기 전에는 조회 not-found나 로컬 타임아웃을 좌석 해제 근거로 사용하지 않는다.

## 5. 다중 예약

같은 운행 일정의 대상은 같은 slot Lua로 처리할 수 있다. 다른 운행 일정은 각각 전환하고 모든 대상의 성공을 DB에 기록한 뒤 외부 승인을 호출한다.

```text
res_A → CONFIRMING 성공
res_B → 만료로 전환 실패
결제사 승인 → 호출하지 않음
res_A → 동일 attempt의 승인 중단 확정 후 보상
```

한 예약의 전환 응답이 유실되면 실제 상태를 같은 attemptId로 다시 확인한다. Redis 단순 예외를 전환 실패 확정으로 취급하지 않는다. 부분 전환 후 실패 정책은 기본적으로 해당 결제 시도를 종료하고 점유를 취소하는 방향이며, HELD로 되돌려 재결제를 허용할지는 별도 정책으로 정한다.

## 6. 결과 분기

| 결과 | 후속 처리 |
|---|---|
| 승인 성공·주문/금액 일치 | [예매 확정](09-booking-finalize.md) |
| 명확한 승인 거부 | DB 실패 기록·Outbox → 예약 취소 |
| 타임아웃·연결 끊김·일부 서버 오류 | 결과 불명으로 보존, [결제 복구](10-payment-failure-recovery.md) |
| 이미 처리된 승인 | 기존 DB·provider 결과 대조 후 멱등 반환 |
| 성공 응답의 주문/금액 불일치 | 일반 실패로 즉시 해제하지 않고 결제 결과 대조·보상 |

HTTP 오류 전체를 명확한 실패로 분류하지 않는다. 결제사 오류 의미를 기준으로 분류한다. 이행 불가능한 승인 성공은 취소 확인 후에만 좌석을 해제한다.

## 7. 현재 코드에서 바꿀 부분

- PaymentConfirmService의 클래스 트랜잭션 안 외부 호출을 분리한다.
- 현재 PaymentGateway의 승인 계약에 조회·취소·결과 불명 처리를 확장한다.
- PendingBookingReader/SeatHoldReleaser를 승인 상태 전이 port로 대체한다.
- TTL 생존 확인만으로 승인 가능성을 판단하거나 성공 직후 Hold를 삭제하지 않는다.
- 오류 로그에 paymentKey를 무분별하게 출력하지 않고 attemptId·orderId로 추적한다.

## 8. 수용 기준

- [ ] 만료된 HELD에서 승인 호출이 일어나지 않는다.
- [ ] 중복 요청은 외부 승인을 무조건 재호출하지 않고 기존 시도로 수렴한다.
- [ ] 승인 중 원래 만료 시각이 지나도 다른 사용자가 점유하지 못한다.
- [ ] 전체 대상 진입 완료 이전 외부 호출이 없다.
- [ ] 전송 전/후 프로세스 종료·응답 유실·늦은 실행자를 복구할 수 있다.
- [ ] 타임아웃·금액 불일치·명확한 실패를 구분한다.
- [ ] 성공 경로와 복구 경로를 함께 검증한 뒤 활성화한다.
