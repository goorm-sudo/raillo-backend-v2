# 검증과 운영 전환

[목록](README.md) · [로드맵](roadmap.md) · [설계 기준](01-decisions.md)

## 1. 검증 범위

이 문서의 체크리스트는 앞으로 작성·실행할 검증이다. 문서 작성 단계에서 Java/Lua/테스트 코드를 구현하거나 빌드 통과를 확인한 것은 아니다.

테스트 코드 작성·수정 시 프로젝트 `/test` 스킬을 사용한다. 실제 환경과 맞춘 Testcontainers MySQL 8.4.10·Redis 7.4를 사용하고 Docker를 준비한다. `@ServiceTest`와 cleanup 규칙을 따르며 테스트 메서드에 `@Transactional`을 붙이지 않는다. [테스트 가이드](../testing-guide.md)

## 2. 기능·동시성 수용 기준

| 영역 | 필수 시나리오 |
|---|---|
| 생성 | 유효한 단일/다중 좌석, 잘못된 소속·구간·출발 시간·승객 수 |
| 구간 | 같은 좌석의 겹치는 구간은 거부, 인접 비중첩 구간 허용 |
| 다중 좌석 | 마지막 좌석이 충돌해도 앞 좌석 점유 없음 |
| 멱등성 | 같은 키/같은 payload, 같은 키/다른 payload, 응답 유실, 종료 후 재시도 |
| 기준정보 | 버전 읽기 중 갱신, 미적재, 판매 취소, generation 변경 |
| 만료 | 정확한 경계 시각, Worker 지연, 만료 점유 재사용 후 늦은 정리 |
| 취소 | 사용자 권한, 중복 취소, 취소와 승인 진입 경합 |
| 준비 | 같은 요청 중복 주문 방지, 다른 주문 중복 바인딩 방지, 부분 연결 실패 |
| 승인 | 중복·동시 승인, 만료 직전 진입, 여러 운행 중 일부 전환 실패 |
| 확정 | 하나의 원본 주문에서 중복 Booking·Ticket 방지, 확정 점유 유지 |
| 취소/환불 | 전액·부분 범위, 성공/실패 응답 유실, 중복 취소 |
| 조회 | 논리 만료 표시, 점유 누락을 빈 좌석으로 오해하지 않음, 이중 차감 없음 |

시계 경계 테스트는 고정 sleep에만 의존하지 않고 expiresAt·Redis TIME의 관측으로 판정한다. 필요 이상의 장시간 대기를 만들지 않는다.

## 3. 장애 주입 지점

각 지점의 앞·뒤에서 프로세스 종료 또는 의존 시스템 실패를 주입한다.

1. 예약 Lua 실행 중 부분 쓰기 오류, 실행 완료 후 응답 유실.
2. 준비 의도 DB 커밋 후, Redis 주문 연결 후, 주문 상세 DB 커밋 후.
3. 승인 시도 DB 기록 후, 일부 CONFIRMING 전환 후, 전체 전환 후.
4. 승인 전송 단계 기록 후 실제 HTTP 호출 전, 호출 후 응답 전.
5. 결제 성공 응답 후 예매 DB 커밋 전·후.
6. Redis 확정/취소 반영 후 Outbox 완료 표시 전.
7. 만료 후보 조회 후 Lua 실행 전, 물리 정리 중 실패.
8. 결제 취소 성공 후 응답·DB 결과 저장 전.

관찰 결과는 중복 결제/예매, 점유 조기 해제, 끝나지 않은 작업 누락, 거짓 완료가 없어야 한다. 일시적인 보수적 점유는 추적 가능한 복구 작업으로 남아야 한다.

처리 lease 만료 후 이전 실행자가 다시 움직이는 시나리오를 포함한다. DB fence만으로 외부 요청까지 취소된다고 가정한 테스트는 불충분하다.

## 4. Redis 내구성·판매 차단

Redis를 재고 판단 원본으로 사용할 때 다음을 운영 게이트로 둔다.

- AOF·백업·복제·디스크·메모리 정책과 허용 데이터 유실량 결정.
- 점유 데이터의 임의 eviction 방지. `noeviction`을 선택하면 메모리 부족 쓰기 실패와 그 복구를 검증.
- failover 이후 데이터가 완전한지 검증하기 전 신규 예약·승인 허용 금지.
- Redis 내부 READY 키만으로 외부 failover/유실을 완벽히 탐지한다고 가정하지 않음. 운영 감지·라우팅 차단·복구 시작 조건 필요.
- generation은 늦은 요청을 구분하는 수단이며 이미 유실된 점유를 복원하는 수단은 아님.
- Redis 단독 성공 응답의 내구성 한계에 대한 제품 정책 확정.

Redis 복제는 기본적으로 비동기이며 WAIT도 시스템 전체의 강한 일관성을 자동 보장하지 않는다. [Redis 복제 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

## 5. 점유 복원 절차

```text
판매 차단 / RECOVERING
  → 이전 세대 요청과 작업 실행 통제
  → DB 확정 예매의 활성 좌석·구간 읽기
  → DB 미완료 준비·승인 시도와 결제사 결과 대조
  → 확정 점유 및 보호가 필요한 진행 중 점유 재구성
  → 기준정보·예약 본문·occupancy·인덱스 일치 검사
  → 새 generation 게시 / READY
```

기존 Booking에 reservationId가 없으면 원본 OrderBooking 매핑 또는 복원 전용 식별 규칙이 필요하다. occupancy만 복원하고 소유 Reservation 본문을 생략하지 않는다. 취소된 SeatBooking을 복원하지 않도록 DB 활성 좌석 표현을 먼저 확정한다.

Redis에만 있던 HELD가 완전히 유실된 경우 DB에서 자동 재생성할 수 없다. 이 예약을 무효화하고 사용자에게 재예약을 안내할지, 더 강한 동기 내구성을 요구할지 D9에서 선택한다. 비동기 기록이 유실 0을 보장한다고 설명하지 않는다.

## 6. 기존 상태에서 전환

사용자가 코드를 정리한 것과 운영 데이터가 비어 있는 것은 다르다. 환경별로 다음 중 하나를 선택한다.

| 환경 | 전환 방식 |
|---|---|
| 데이터 없는 개발 환경 | 새 키·스키마로 초기화 후 검증 |
| 진행 중 예약이 있는 환경 | 신규 예약을 차단하고 기존 예약 소진 또는 명시적 마이그레이션 |
| 진행 중 결제가 있는 환경 | 결과를 조회·확정/취소하고 미완료 건을 이관한 뒤 전환 |
| 기존 확정 예매가 있는 환경 | 활성 좌석·구간을 Redis에 적재·대조한 뒤 판매 |

구/신 예약 API가 서로 다른 점유표에 동시에 쓰게 하지 않는다. 판매 차단 기간, 진행 중 요청 처리, 기존 멱등성 키 처리, 복구 담당자·중단 기준을 실행 전에 기록한다.

롤백 역시 판매를 차단하고 신규 예매·예약을 구 시스템이 인지하도록 동기화해야 한다. 애플리케이션 버전만 내리고 구 Hold 키로 판매를 재개하지 않는다.

## 7. 성능·관측

- 예약 생성 정상 경로 DB 조회·쓰기 0 확인. 인증 등 요청 전처리 범위는 측정에서 구분.
- p50/p95/p99 지연, 동시 요청 처리량, 충돌률, Redis CPU·메모리·명령 수 측정.
- 요청 좌석 수·구간 길이에 따른 Lua 시간, 인기 운행 일정의 단일 slot 부하 측정.
- 좌석 조회의 큰 배치가 생성 Lua 지연에 미치는 영향 측정.
- 가장 오래된 만료 후보·CONFIRMING·Outbox 지연과 재시도·운영 복구 건수 추적.
- 핵심 HASH의 종료 데이터 증가량과 정리 속도 측정. Redis 키 개수가 적어도 메모리가 작다는 보장은 없음.
- 목표 수치는 제품 지연 요구와 부하 모델로 확정. 기존 구조보다 빠르다고 측정 없이 주장하지 않음.
