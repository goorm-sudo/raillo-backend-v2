# 설계 기준과 미결정 사항

## 1. 구현 기준

| 항목 | 선택한 방향 |
|---|---|
| 용어 | 예약 = Reservation, 예매 = Booking, 승차권 = Ticket |
| 예약 저장 | Redis. SeatReservation은 Reservation에 포함하는 값 객체 |
| 예매 저장 | DB Booking·SeatBooking·Ticket |
| 예약 API | 준비된 Redis 기준정보로 검증·운임 계산, 정상 생성 경로 DB 조회 없음 |
| 원자적 범위 | 하나의 운행 일정에 대한 여러 좌석·구간·예약 상태 변경 |
| 구간 표현 | 출발 정차 순서 이상, 도착 정차 순서 미만인 `[departure, arrival)` |
| 시간 | Lua 판정 시 Redis TIME, 교환 형식은 UTC epoch milliseconds |
| 예약 만료 | HELD와 expiresAt으로 논리 판정, deadlines ZSET과 Worker로 정리 |
| 결제 준비 | HELD 유지, 기존 만료 시각 유지, 주문 연결 |
| 승인 진입 | 모든 대상 예약을 CONFIRMING으로 전환한 후 외부 승인 호출 |
| 확정 | DB 예매 커밋 후 CONFIRMED 반영, occupancy 유지 |
| 이벤트 | 예약 Redis Stream·생성 이벤트·Consumer 제외 |
| DB Outbox | DB 상태 확정과 Redis 반영 사이의 재처리 기록으로 유지 |

## 2. 상태 전이

| 출발 상태 | 명령·조건 | 도착 상태 | 점유 |
|---|---|---|---|
| 없음 | 예약 생성 성공 | HELD | 요청한 모든 구간 설정 |
| HELD | 동일 주문 연결 | HELD | 유지, expiresAt 변경 없음 |
| HELD | 사용자 취소 | CANCELLED | 본인 소유 구간만 해제 |
| HELD | expiresAt 이하로 현재 시간이 도달 | EXPIRED | 본인 소유 구간만 해제 |
| HELD | 만료 전, 주문·승인 시도·점유 검증 | CONFIRMING | 계속 유지 |
| CONFIRMING | DB 예매 커밋 확인 | CONFIRMED | 계속 유지 |
| CONFIRMING | 실패·취소가 확정되고 늦은 승인이 불가능함을 확보 | CANCELLED | 본인 소유 구간만 해제 |

EXPIRED는 Worker가 기록하기 전에도 시간상 만료된 HELD를 조회 응답에서 나타낼 수 있다. 저장 상태와 유효성을 혼동하지 않는다. CONFIRMING에서 원래 expiresAt은 자동 해제 조건이 아니다.

CONFIRMED의 부분 취소는 위 예약 상태만으로 표현하지 않는다. DB 취소 내역과 Reservation의 취소된 좌석 범위/적용 순서를 기록하고 해당 occupancy만 해제한다. 모두 취소된 경우의 종료 표현은 [예매 취소](11-booking-cancel.md)에서 확정한다.

## 3. 정합성 규칙

1. 유효한 운행·좌석·구간만 예약할 수 있다. 운행 정보 미적재를 빈 좌석으로 해석하지 않는다.
2. 다른 유효한 예약의 점유와 겹치는 요청은 전체 거부한다. 모든 구간을 먼저 검사한 후 쓴다.
3. occupancy가 가리키는 예약 본문이 없다면 정합성 오류다. 임의로 재판매하지 않는다.
4. 해제 시 현재 점유 소유자, 상태, 주문·승인 시도, 복구 세대를 대조한다.
5. 하나의 예약을 다른 활성 주문에 중복 귀속하지 않는다. 중복 승인·예매 생성은 DB에서도 방지한다.
6. Redis와 DB와 결제사는 하나의 트랜잭션이 아니다. 각 경계에 영속 진행 기록과 보상·재조회 경로를 둔다.
7. 결제 성공 후 DB 확정이 지연되면 좌석을 보호한다. 결제 취소로 보상할 경우 취소 결과 확인 전에는 해제하지 않는다.
8. Redis replica 조회는 예약 승인 판단의 근거로 사용하지 않는다. 쓰기를 수행할 primary의 상태를 검사한다.
9. 원본 점유를 바꾸는 경로는 정의된 Lua와 판매 차단 상태의 복구 작업으로 제한한다.

## 4. 대화에서 보완한 부분

### TTL 대신 ZSET을 선택한 이유

키 전체 TTL과 예약별 유효기간은 다르다. 또한 Redis 7.4에는 [HASH 필드 만료 명령](https://redis.io/docs/latest/commands/hexpire/)이 있으므로, HASH 필드에 만료를 설정할 수 없어서 이 구조를 선택한 것은 아니다.

예약 본문이 자동 삭제되기 전에 상태·좌석 소유자를 확인해 여러 자료구조를 정리하고, CONFIRMING을 별도 복구 대상으로 관리하기 위해 expiresAt+ZSET을 선택한다. 종료 데이터의 물리 삭제와 일반 캐시의 TTL까지 금지하는 결정은 아니다.

### Lua 원자성과 장애 시 롤백

Lua 실행 중 다른 명령이 끼어들지 않는 성질과, 실행 도중 오류가 나면 이전 쓰기를 되돌리는 성질은 다르다. 입력·키 타입·크기 등을 쓰기 전에 검증하고, 부분 쓰기 오류는 operation ID와 정합성 검사로 복구한다. [Redis Lua 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/)

### 결제 준비의 영속 진행 기록

단순히 `Redis 주문 연결 → DB INSERT`만 구현하면 그 사이 프로세스 종료를 추적하기 어렵다. 주문 연결 전에 준비 요청과 안정적인 orderId를 DB에 기록하는 방안을 보완 제안한다. 준비 기록 테이블을 추가할지 Order의 준비 단계를 확장할지는 미결정이다. [결제 준비](07-payment-prepare.md)

### 승인 처리 권한과 외부 호출

DB lease 만료는 작업자를 교체하는 신호일 뿐, 이전 작업자가 외부 승인을 호출하지 않을 것이라는 증거가 아니다. 승인 전송 단계 기록, 이전 실행자 차단, 결제사의 멱등성·조회 계약을 함께 정해야 한다. 단일 조회 not-found만으로 실패를 확정하지 않는다. [실패·복구](10-payment-failure-recovery.md)

## 5. 구현·배포 전에 결정할 항목

2026-09-09 예약 생성 구현에서는 기존 할인율·반올림 없음, 최대 8석, 기본 10분·마감 여유 0초, 회원·운행별 멱등성, HTTP 201과 UTC ms 응답을 적용했다. [구현 현황](18-reservation-create-implementation.md)의 기본값이며 D1의 할인 자격·통화 제약, D3/D5의 보존 기간 등은 여전히 후속 결정 사항이다.

| ID | 항목 | 권장 방향 / 결정할 내용 | 결정 기한 |
|---|---|---|---|
| D1 | 예약 운임 정책 | 유효기간 내 예약 운임 고정 권장. 반올림·통화 단위·할인 자격 검증도 명시 | 예약 생성 |
| D2 | 예약 한도·시간 | 최대 좌석 수, 기본 유효기간, 출발 전 판매 마감. 문서의 10분은 예시 | 예약 생성 |
| D3 | 멱등성 | 회원·운행 일정별 scope, canonical 요청 hash, 보존 기간·재시도 응답 | 예약 생성 |
| D4 | 조회·탐색 인덱스 | 회원 목록, Worker 운행 목록, 비원자 갱신의 누락 복구 방식 | 조회·Worker |
| D5 | 보존·용량 | 종료 예약·멱등성·확정 점유의 정리 시점, HSCAN/추가 인덱스 | 만료·정리 |
| D6 | 결제 준비 기록 | 준비 작업 테이블 또는 Order 준비 상태, 실패 후 재준비 정책 | 결제 준비 |
| D7 | 승인 실행 계약 | attempt 모델·전송 단계·lease·provider 멱등성 범위·늦은 실행자 통제 | 승인·복구 |
| D8 | 부분 취소 | 좌석별 취소 범위·환불 금액·적용 순서·중복 취소 방어 | 예매 취소 |
| D9 | 내구성·복구 | 허용 예약 유실량, Redis 영속성·failover 정책, 판매 차단 경로 | 실판매 활성화 전 |
| D10 | 공개 API | 요청/응답·HTTP 상태·에러 코드·복구 중 UI 표시·시간 형식 | API 연동 |
| D11 | 출시 범위 | 단일 예약 결제부터 시작할지, 다중 운행 주문까지 활성화할지 | 로드맵 0단계 |
| D12 | 지연 결제수단 | 가상계좌·입금 Webhook 등은 별도 점유·만료 정책 필요 | 해당 수단 활성화 전 |

이 표의 미결정은 문서 미작성이 아니라 실제 정책 선택이 필요한 경계다. 해당 단계의 완료 조건에 포함하고 결정 후 표를 갱신한다.
